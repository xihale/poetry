# 诗

一个诗选的艺术站点。打开抽一首，满屏一首；上滑或下滚一次翻一页，就是下一首。
12.5 万首：中国古典三十部，加上现代诗与五部外国诗（含一部中英对照）。
题目下的作者、时代、诗集、卷次都可以点：点开就在那行字旁边列出一轴的全部选择与诗数，
挑一行才换诗。也可以按诗集、部类、卷次、时代、作者、体裁、语言、情绪、视角、篇幅
十个维度挑着读，或者在全部诗句里**寻句**——记得半句就能找到它。

没有首页，没有目录，没有导航栏，屏幕上也没有任何状态文字。
屏幕上只有诗，和右下角淡到几乎看不见的两个字：寻句、分类。

现代诗那一批仍在著作权保护期内，所以它们的解题位置写着一行来源声明——
这是全站唯一一句与诗无关的字，是收录它们的代价。

## 十个维度怎么来的

编排字段与文本字段分开：

- **诗集 / 部类 / 卷次** 来自各书自己的目录（乐府诗集·相和歌辞·卷二十六、
  诗经·国风·周南、花间集·卷四）。是编排，不从正文猜；书没有卷号的，卷次留空。
  卷次一轴把「卷一」与「卷1」按同一个序数排，因为两部书用两种写法写同一件事。
- **语言** 是页面文字的语言。飞鸟集是中文（郑振铎译本），它下面那半英文的语种写在
  另一个字段里，所以筛选「英文」不会把一本中文书筛进来。
- **时代** 优先取作者旁的朝代标记；只写名字的，用这位作者在同一批书里
  别处的标注补上；再补不上就留「不详」，不猜。
- **体裁** 读句读长度：单句超过 20 字为文（标题以「赋」结尾为赋）；
  句长 75% 以上落在 7/6/5/4/3 字即七言/六言/五言/四言/三言；否则杂言。
  词与楚辞另有标记。
- **情绪**、**视角** 是词表命中：收「愁」是因为诗里真的有愁/泪/断肠，
  收「你」是因为有劝君/思君这类第二人称短语（「君子」不算）。每一条都能在屏幕上核对。
- **篇幅** 按字数分短/中/长；拉丁字母诗按 1/1.8 折算，否则同样宽度的一首英文诗会被算成两倍长。
- **体裁** 对现代诗是「新诗」，对外国诗是「十四行诗」「散文诗」或「诗」——
  白话诗按句长去猜会把它读成五言，这是书的性质，不该推断。

正文一律**一句一行**：源文件有的地方整首排成一行、有的已经分句，
保留源里已有的换行（它可能是标点表达不了的分段），剩下的长句再按句读切。

## 寻句

在 125,314 首里做**子串**查找，分两轮：先找真正含有这串字的诗，一首都没有时
再放宽一次。诗站要有搜索的理由就是那半句记得住的诗（「明月几时有」），
而那是正文里的子串——标签怎么索引都答不了；放宽的那一轮，是给记错了半个字的人的。

- **索引是二元组（bigram），不是词。** 中文没有词边界，词索引要分词器和词典，
  而且跨词边界的短语仍然找不到。二元组索引对任何子串查询都是精确的，
  而且没有分词器可以弄错。
- **按哈希分 8,192 片。** 六字查询只用 5 片、几十 KB，浏览器永久缓存，
  而不是 24 MB 全量。片按 gzip 存放，最坏一片 7 KB。
- **候选之后还要核对。** 索引说的是「这些诗含有查询的每一个二元组」，
  那不等于含有查询本身（「明月」和「月几」都出现，不等于「明月几」）。
  所以每个候选都拿真实正文再确认一遍——答案因此是精确的，而不只是像。
- **全落空了就退一步。** 没有任何一首真的含有这串字时，寻句不再只答
  「没有这一句」：候选改为与查询共享两个以上二元组的诗，仍逐首对正文核对。
  「兰陵王·凤啸咽」就这样找回「兰陵王·凤箫咽」——兰陵、陵王、王凤三个二元组
  还系着它，题目与查询只差一个字，就排在最前。排序先看共享的二元组数，
  再看那一行与查询共用的字；标出的是实际命中的片段。它不猜你写错了哪个字，
  只把查询还可能是的那些诗摆出来。这一轮不取任何新分片，用的就是精确那一轮
  已经取回的同一批。
- **正文分片本来就是按需取的**，核对几乎不额外花钱：命中的那一首本来就要取。
- 索引里同时收**题目**和**正文**，所以「静夜思」当题目找得到，当句子也找得到。
- 大小写与标点都归一化，所以 `Shall I compare` 与 `shall i compare` 是同一个查询，
  跨换行、跨逗号的短语也能命中。

```
bun run search   # 从 public/corpus/t/ 生成 public/corpus/search/（8,192 片，gz 存放）
```

界面上：右下角「寻句」，或者在读诗面上直接打字——任何可打印字符都会开面板并带上那个字。
↑↓ 移动、回车读、Esc 合上。结果显示**查询所在的那一行**而不是整首，
命中的字用墨色标出；放宽的那一轮，显示的是承载最多命中二元组的那一行。

## 语料怎么发给浏览器

125,314 首不能是一个 JSON，也不该让每个读者为整个语料付一次钱。
四样东西在不同时候取：

| 文件 | 内容 | 大小 |
| --- | --- | --- |
| `public/corpus/facets.json.gz` | 十个维度各自的**取值表**，以及每个取值在整个语料里的计数，构建时算好 | 44 KB gzip |
| `public/corpus/col/<轴>.bin.gz` | 一根轴的**编码列**：每首一个 1–2 字节的码，按取值表的顺序 | 0.1–0.2 MB 原始、最大 71 KB gzip |
| `public/corpus/t/NNNNN.json.gz` | **二十首**诗的题目、正文与标签，装在同一份文件里 | 平均 3.3 KB gzip，最大 60 KB |
| `public/corpus/search/NNNN.bin.gz` | 二元组索引，8,192 片，查询用到哪片取哪片 | 共 24.5 MiB，单片最坏 7 KB |

一份文件不再承担两件事，是这件事能成立的原因：

- **抽一首诗只取一份文件。** 标签就和正文装在同一个分片里，所以点开就是诗，
  前面不需要任何索引；一个没筛、没搜、没开面板的读者，语料上只付约 **6 KB**
  （两份二十首的分片），实测到第一片叶子 63 ms。
- **筛选才需要看每一首的标签。** 那就是编码列，一根轴 0.1–0.2 MB 原始、
  最大 71 KB gzip，只取筛选用到的那几根；面板要把十根轴的新计数都显示出来，
  所以它一次取十根（共 201 KB gzip），之后整个会话不再取。
  旧版是所有人一进门先付 11 MB 来换这个。
- **计数是语料的事实，不是每次重算的东西。** 没有筛选时，面板上的数字是构建时
  算好的，打开面板只取那一个 44 KB 的文件、一根列都不取。
- **只筛一个轴时只取一根列。** 点标签开出的选择器取两根（筛的那根 + 它自己那根）。

筛选后的重算因此是**一次**扫描十根轴共用：池子扫一遍（7 ms），
十个计数在这份 id 列表上走一遍（28 ms）。旧实现在同一件事上是 198 ms，
而且每次筛选要重新过十遍 125,314 首。

标签在分片里与编码列里各存一份，这是有意的：两份都由同一次遍历产生，
所以不可能互相矛盾，而抽到的那首诗因此只需要一份文件。

三个无法编译进去的事实由 `scripts/build-corpus.py` 生成到 `app/corpus-meta.ts`
（诗数、每片几首、轴的顺序）——为三个数字多走一趟往返不值得。轴的顺序在那里生成、
在应用里**按名字**读取，所以调整顺序不会让某个标签印到别处。

## 翻页

阅读面是**一页一次**的：滚轮、触控板、翻页键都只被读成一次手势，触屏一次按下翻一页。
翻过一页的手势随即作废，输入安静 140ms 以上才重新计数——所以触控板的惯性和猛滚
都不会连翻几页。一页是一个视口高，比屏幕高的长诗（如焦仲卿妻）因此要两下手势读完，
像翻书而不是被吸到某首诗的边界。

参数在 `app/pages/index.vue`：`STEP` 24（一次手势的累计行程）、`GAP` 140（两次手势之间的静默）、
`SWIPE` 28（触屏行程）。`prefers-reduced-motion` 下不做平滑滚动。

## 开发

```bash
bun install
bun run dev          # http://localhost:3000
```

重新生成语料与字体（产物都已提交，只有改源数据时才需要）：

```bash
bun run corpus       # .cache 里的来源 -> public/corpus/{facets.json.gz, col/, t/}
bun run corpus-check # 校验四份产物互相一致（列 / 取值表 / 计数 / 分片里的标签）
bun run search       # 正文分片 -> public/corpus/search/（二元组索引，gz 存放）
bun run fonts        # 按语料重新子集化 -> public/fonts/song.woff2
bun run contrast     # 从 CSS 令牌重解对比度，低于阈值即失败
```

`scripts/build-fonts.py` 需要系统里的 Noto Serif CJK SC Light；
若语料里出现扩展 B 区生僻字，它会再生成一个 `rare.woff2` 伴随字体，
没有生僻字时则删除该文件，不白下载。

## 构建与部署

```bash
bun run generate     # 静态站输出到 .output/public
```

站点部署在 `https://poetry.xeed.ink`：推到 `main` → GitHub webhook → gx 上的
`poetry-ci` 接收器（systemd socket 激活，空闲零进程）→ `scripts/server/deploy.sh`
构建并 rsync 到 `/srv/poetry/`，详见 `scripts/server/README.md`。

`nuxt.config.ts` 里的 `baseURL` 跟着 `NUXT_APP_BASE_URL` 走；根路径部署不用设。

**站点里的每一条数据路径都必须是 site-relative（以 `/` 开头），由
`app/utils/bytes.ts` 的 `fetchBytes` 统一拼上 base。** 少拼一处，就是「本地好、
部署上去 404」——绝对路径 `/corpus/...` 解析到的是**域名根**，不是子路径，
而 `public/` 下的东西又恰恰不在 HTML 里，所以这一类失败只在真实部署上出现。

base 由 `app/plugins/base.ts` 从 `app.baseURL` 取（`/` 开发、`/poetry/` 项目页），
**不要用 `import.meta.env.BASE_URL`**：那是 *bundle* 的 base，Nuxt 开发服务器把它设成
`/_nuxt/`（它就在这个前缀下提供应用模块），于是语料会被请求到
`/_nuxt/corpus/t/05479.json.gz` —— 只在开发环境错，而开发环境恰恰是最该对的地方。

验证要跑三处，缺一个就会漏掉一半情况：

```bash
bun run dev                                            # 开发：应当 /corpus/...
bun run generate && cp -r .output/public/. /tmp/site/  # 根：应当 /corpus/...
NUXT_APP_BASE_URL=/poetry/ bun run generate            # 子路径：应当 /poetry/corpus/...
```
（子路径那份把 `.output/public` 放进一个 `poetry/` 子目录下再打开，看有没有 404、叶子有没有出来。）

## 缓存

gx 上的 Caddy 块与 `fetchBytes` 的 URL 约定是一套契约，改一处要过另一处：

- `/_nuxt/**` 文件名带内容哈希 → `max-age=31536000, immutable`；
- `/corpus/**` 路径不带哈希，靠 `fetchBytes` 给每个请求加上 `?v=CORPUS_BUILD`
  （`app/corpus-meta.ts` 的戳）→ 同样 `immutable`。语料一换，戳一换，URL 全换，
  老缓存自然作废；服务器侧旧文件退役进 attic（7 天），撑住部署那一瞬还在读的会话；
- `/fonts/**` 无哈希，7 天 + ETag；换字体要换文件名或手动清缓存；
- HTML（`/`、`200.html`、`404.html`、`_payload.json`）→ `no-cache`，靠 ETag 304，
  首屏 HTML 只有 4 KB，这一来新部署永远立刻可见；
- 语料文件本身已是 gzip，`encode` 对 `/corpus/**` 豁免——再压一层白烧 CPU。

## 对比度

每一个墨色都是 `app/assets/css/main.css` 里的一个令牌，并且都对着自己的纸色解出来，
不是眼睛看的：`--ink` ≥ 7:1（正文，AAA），`--faint` ≥ 4.5:1（标签与计数是 11–13px 的正文），
`--ghost` ≥ 3:1（最淡的一档，只用于刻意无效的空选项和翻页记号），`--line` ≥ 1.6:1（线要看得见）。
`python3 scripts/check-contrast.py` 从样式表本身重新解一遍，任何一档掉下去就失败。

最近一次调整把 `--faint` 从 4.66:1 提到 6.23:1（暗色 7.41:1），`--ghost` 从 2.00:1 提到 3.13:1，
并把两个真正的控件（「其余」与续页记号）从 `--ghost` 提到 `--faint`。

## 来源与边界

古籍全文与解题来自古文岛公开页面；九部古典来源来自 chinese-poetry 镜像；
